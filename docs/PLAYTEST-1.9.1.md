# DetergentMC 1.9.1 実機プレイテスト — チェックリスト

2026-11-19 作成、Stage A〜D 完了に合わせて作成。1.9.1 クライアント
（プロトコル108）で各サーバーに参加する実機確認のための手順と、

## 0. この手順書の読み方

DetergentMC の 108 対応は **Stage E まで完了**。単体テスト
（分割検証 4,431 件・失敗 0）と実バニラ統合テスト（新規 3 セル
＋回帰 62 セルの 65 セルすべて合格）で確認済みだが、
**本物のゲームクライアントでの確認は未実施**。この
チェックリストはその実機確認のためのものである。

108 は 1.9.1 単独プロトコルで、109（1.9.2）とは差分ゼロ
（実 jar 同士の全面比較とワイヤ採取で証明済み）。実機での
重点は 109 から引き継ぐ項目がそのまま当てはまる：
**チャンクのブロックエンティティ欠落の見え方**（看板の
文字・チェストの中身が 108 経由では出ない）、**看板の
ライブ更新が届かないこと**、**近似の見え方**と **Keep Alive
（varint）の長時間セッションでの安定性**。

### A. 単体テストで検証済みの項目（実機では再現の確認）

- 108 のパケット ID 列が 109 と全エントリ完全一致すること
  （`PacketIds108Test`：全 284 エントリで id108 == id109 を
  固定。108 に存在するのは 114 件）。
- 対応クライアント一覧の最古が 108 で、109／110／210／315／
  316 が残り、計 39 プロトコル（`ClientAdapter108Test`。
  最古脱落の罠を固定）。
- レジストリ写像が全入力域で 109 と一致すること
  （`RegistryRemapper108Test`。委譲の正しさを固定）。
- チャンクの blockEntities 欠落の境界処理
  （`ChunkTranslator108Test`：108 形式に末尾が無いこと、
  758 側のブロックエンティティが 108 向けで落ちること、
  108→758 で空の列が補われること）。
- クライアント行き update_sign が正準経路で落ちること、
  sound_effect が 108 では 0x47 で届き pitch が u8 化される
  こと（`ProxySession108Test`）。

### B. 実機でしか確認できない項目

- [ ] 1.9.1 クライアントで 1.9.1 サーバー（内部）に参加し、
      チャンク表示・移動・チャットが正常か。
- [ ] 1.9.1 クライアントで新しいサーバー（例：1.20.4）に
      参加できるか。音のピッチが極端にずれて聞こえないか。
- [ ] 新しいクライアント（例：1.20.4）で 1.9.1 サーバーに
      参加し、看板の文字・チェストの中身がどう見えるか
      （108 のチャンクにはブロックエンティティが載らない
      ため、欠落が前提。エラーや切断にならないことの確認）。
- [ ] 1.9.1 サーバー側で看板を書き換えたとき、新しい
      クライアントにライブ更新が届かないこと（仕様どおりの
      制限であることの確認。切断やエラーにはならないこと）。
- [ ] リソースパックの要求→応答の流れが 1.9.1 クライアントで
      完走するか（空 hash の受け付け自体は Stage E で実バニラ
      1.9.1 が受け付けることを確認済み。ここでは実クライアント
      での流れ全体を見る）。
- [ ] polar_bear のいる場所でブタとして表示されるか
      （1.9.1 クライアント→新しいサーバー）。
- [ ] Keep Alive（varint）世代のため、30 分以上の接続で
      切断されないか。
- [ ] 2 人以上のプレイヤーが互いに見えるか（全バージョン
      共通の最優先確認項目。偽クライアントでは検証不能）。
