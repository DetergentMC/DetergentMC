# プロトコル23（Minecraft 1.1）対応ノート

DetergentMC のレガシーフロントエンド（`detergentmc-legacy-frontend`）がプロトコル23
（**1.1**）を受けられるようにした記録。Stage A の実測が正であり、
本文書の数値はすべて実 jar・実バニラからの採取に基づく。

番号対応：**23 ＝ 1.1**（先行調査 `legacy-prep-final/PREP-FINAL.md` の
ログイン探査＋jar 内定数の二重確認で実測）。23 は Netty 以前世代の番号であり、
legacy モジュール内にのみ置き、`ProtocolVersion` には入れない。

実サーバー jar の入手経路は 28 と同じ（Omniarchive Vault の jar を
公式 .exe 配布物とバイト単位で照合済み）。

## Stage A：実測（1.1 サーバー jar、JDK 8）

- バニラ 1.1 サーバー jar SHA-1 `3dbadea4e8a0923ac5fde9f4b9e98a244ea2589a`
  （ディスクで再検証済み）。
- パケット登録は jar から機械抽出（基底クラス `kq`）。**登録 65 件**
  （28 は 67 件）。方向フラグは共通パケットすべてで 28 と同一。
- **28⇔23 の差分**：共通 65 件、28 にだけある 2 件、形式差分 6 件。
  - **28 にだけある**：0x23 entity_head_look、0x84 tile_entity_data
    （どちらも 1.2 の追加。23 向けには頭の向きパケットを落とし、
    タイルエンティティデータは 29 世代と同じく落とす）。
  - **形式差分 6 件**：
    1. **0x01 login が過渡形**：[protocol I32, ユーザー名 STRING,
       **seed I64**, levelType STRING, gamemode I32, dimension I8,
       difficulty I8, worldHeight I8, maxPlayers I8]（応答も同形で
       entityId／""／seed／levelType／…）。28 の形との違いは
       seed の位置と末尾（dimension が I32→I8、U8×4 になる）。
       フィールドの意味はログインクラス `nx` の書き込み側と
       サーバーの構築箇所で確定（gamemode→dimension→difficulty→
       worldHeight→maxPlayers の順）。
    2. **0x09 respawn に seed がある**：[dimension I8, difficulty I8,
       gamemode I8, worldHeight I16, **seed I64**, levelType STRING]
       （28 は [dimension I32, I8, I8, I16, levelType]）。
    3. **0x18 spawn_mob の回転バイトが 2 本**（yaw、pitch）。
       28 の 3 本目（頭の yaw）は無い。
    4. **0x33 chunk_data が直方体（キューボイド）形式**：
       [x I32, y I16, z I32, sizeX U8, sizeY U8, sizeZ U8
       （いずれも個数−1）, 圧縮長 I32, データ]。データの中身は
       キューボイド全体について「ブロック ID 配列（1 バイト／個）、
       メタデータ nibble 配列、ブロック光 nibble 配列、
       天空光 nibble 配列」の順で、インデックスは
       `(lx × sizeZ + lz) × sizeY + ly`（y が最速）。
       チャンククラス `kr` の抽出メソッドと NBT タグ対応
       （Blocks／Data／SkyLight／BlockLight）で確定。
       膨張後の長さは実測で `n + 3×ceil(n/2)`（n＝ブロック数）と一致。
       セクション形式（28／29）とは別形式のため専用コーデックが要る。
    5. **0x34 multi_block_change が 3 配列形**：[chunkX I32, chunkZ I32,
       count U16, 座標 count×I16, 種別 count×U8, メタ count×U8]。
       座標 I16 の詰めは `(localX << 12) | (localZ << 8) | y`
       （パケットクラス `xg` の構築側で確定）。28 の
       「長さ付きバイト配列」形とは別形式。
    6. 0xFA plugin_message は抽出器のトークン化の差だけで、
       ワイヤは同一（差分として数えない）。
  - 0x17 spawn_object は 28／29 と同じ「回転バイト無し＋速度は
    data > 0 のときだけ」形（クラス `sf` の読み取りで確認。
    共有コーデック `spawn_object_norot` の velocity 条件は
    `data != 0` で、実 jar の `data > 0` とは負値のときだけ違う。
    バニラは負値を送らないため実害は無いが、実測としては記録する）。
- レジストリ（実 jar のランタイム反射で抽出）：
  - ブロック 122 種：28 から **123／124（レッドストーンランプ）が無い**。
  - アイテム 139 種：28 から **384（経験値ボトル＝bottle o' enchanting）、
    385（ファイヤーチャージ）が無い**。
  - ダメージ可能アイテム集合は **49 件**で 28／29 と完全同一
    （スロットの条件付き NBT は同じ集合でそのまま使える）。
  - エンティティ（EntityList 登録）：28 から **オブジェクト 16
    （投げポーション登録）、17（経験値ボトル登録）、モブ 99
    （アイアンゴーレム）、モブ 98（ヤマネコ）が無い**
    （いずれも 1.2 の追加）。
  - **ただしスポーンの実測は登録と違う**（Stage B でトラッカー
    クラス `ij` を読んで訂正）：1.1 のトラッカーは投げポーションを
    **種別 73（data＝ポーションの値）で実際に生成する**。スプラッシュ
    ポーションは 1.0 の時代から存在し、EntityList に登録が無いのは
    登録漏れに近い扱いである。経験値ボトル（種別 75）の生成は
    1.2.5 のトラッカーにのみあり、1.1 には無い。落下ブロックは
    ブロックごとに種別が違う（70＝砂、71＝砂利、74＝ドラゴンの卵）
    ことも 1.1／1.0.0 のトラッカーで確認した（現代側のアイテム
    フレーム種別 71 は 1.1 では「落下する砂利」を意味する）。
  - スロット形式：平スロットは条件付き NBT（上記 49 件の集合、
    基底クラス `kq` の読み取りは `g() || i()` だが `i()` を
    上書きするアイテムは jar 内に存在しないため実質 `g()` のみ）。
    DataWatcher（クラス `tm`）は型 0〜6 で、型 5 のスロットは
    id／個数／ダメージのみ（NBT 無し）＝28／29 と同一。
- 採取による裏付け（実バニラを JDK 8 で起動し平文ログイン）：
  - 先行調査の採取（433 パケット）を抽出表で最後まで解析しズレゼロ。
  - 本 Stage A の自前採取：ログインのみ 167 パケット、位置パケットを
    送ってチャンクを引き出した採取 4,353 パケット（0x33 キューボイド
    多数を含む）もズレゼロ。キューボイドの膨張長は全件で
    `n + 3×ceil(n/2)` と一致。
  - 1.1 のサーバーはログイン直後に 0x32 pre_chunk×121 を送るが、
    0x33 はクライアントの位置パケットを受けた後、送信キューが
    空に近いときに 1 件ずつ流れる（実測で確認した挙動）。
  - ログイン応答の実測値：[entityId, "", seed, "FLAT", gamemode 0,
    dimension 0, difficulty 1, worldHeight 128, maxPlayers 20]。

## 近似・落とすもの（23 向け）

- **レッドストーンランプ（123／124）→ グロウストーン（89）**：
  28 の層で寄せる（23 は 28 の層を継承するため自動的に同じ近似になる）。
  点灯／消灯の区別は失われる。
- **経験値ボトル（384）→ ポーション（373）**、**ファイヤーチャージ
  （385）→ 火打石と打ち金（259）**：28 の層で寄せる。
- **ヤマネコ（モブ 98）・アイアンゴーレム（モブ 99）→ ブタ（90）**：
  ウィザー／コウモリ／魔女と同じ置換方針。
- **経験値ボトル（オブジェクト種別 75）のスポーンは落とす**：
  1.2 の追加エンティティ（花火と同じ方針）。**投げポーション
  （種別 73）は落とさない**：1.1 のトラッカーが実際に生成する
  ため、そのまま通す（Stage A 初稿の「73 も落とす」は EntityList
  登録だけを見た誤りで、Stage B のトラッカー実測で訂正した）。
- **アイテムフレーム（オブジェクト種別 71）のスポーンは落とす**：
  1.4 の追加エンティティのため。なお 23 世代では種別 71 は
  「落下する砂利」を意味するので、通すと誤表示になる。
- **トロッコのバリエーション**：現代側の data 1（チェスト）→
  種別 11、data 2（かまど）→ 種別 12（1.1 は別種別で表す）、
  data 3〜6（TNT／スポナー／ホッパー／コマンド）は通常の
  トロッコ（種別 10、data 0）に落とす。
- **チャンクの高さは 128 まで**：現代側セクション 8〜15
  （y 128〜255）はキューボイドに載せられず落とす（1.1 の
  ワールド高さ自体が 128）。バイオーム配列も落とす
  （23 のクライアントは seed から自前で計算する）。
- **ログイン／リスポーンの seed はブリッジモードでは 0**：
  現代側に seed が無いため。23 のクライアントはバイオームの
  色合いを seed から計算するので、見た目の色味だけが変わりうる
  （ダイレクトモードでは実バニラの seed がそのまま通る）。
- **0x23 entity_head_look は落とす**（パケットが無い）。
  頭の向きは 0x18 の yaw で近似される。
- 28／29 世代の近似も継承する（詳細は `docs/PROXY-1.2.5.md`）。

## Stage B〜D：実装

- パケット表：`LegacyPacketTable` の V1_1 は V1_2_3 から 0x23／
  0x84 を除き、0x01／0x09（seed 形）、0x18（回転 2 バイト）、
  0x33（キューボイド専用コーデック `chunk_data_cuboid`）、
  0x34（初期形コーデック `multi_block_change_early`）を差し替えて
  構成（差分をテストで固定）。
- チャンク：ブリッジモードでは現代側セクション形式を
  `LegacyChunkRemap.remapChunkToCuboid` でキューボイドへ再配置し、
  0x32 pre_chunk の後に 0x33 として送る。y 128 未満に何も残らない
  チャンクは pre_chunk だけになる。
- ログイン：平文経路（29／28 と共用）。ブリッジのログイン応答は
  9 フィールド形（seed 0、高さ 128）。
- アダプタ：`V1_1Adapter` を ServiceLoader 登録。コア配線
  （`minecraft-version: 1.1`、内部バニラ Java 8、versionedJars）も
  追加済み。jar は piston-meta に配布が無いため手動配置が必要
  （SHA-1 は本書 Stage A の記載どおり）。
- **Stage E（実バニラ統合テスト）は完了**（2026-11-20、下記
  Stage E 節）。残る未確認は本物のゲームクライアントでの
  確認のみ。とくにブリッジモードでアイテム実体を 0x17
  種別 2 で送る方式の実クライアント受け可否は未確認
  （`docs/PLAYTEST-1.1.md` の最重点項目）。

## Stage E（実バニラ統合）完了（2026-11-20）

29 の Stage E 最終 HEAD `71c2370` へリベースし、新規セルを
追加した（28／23／22 合計 12 件）。23 のセルは：ブリッジ
fake23 → 実バニラ 1.7.10、ダイレクト fake23 → 実バニラ 1.1
（平文ログイン、jar は手動配置、SHA-1
`3dbadea4e8a0923ac5fde9f4b9e98a244ea2589a`）、§1 ピング
完全形（23／"1.1"）、素の FE 01 への旧形式応答。
参加系はすべて「参加→チャット→Keep Alive 応答→応答後の
2 通目のチャット到達」を実バニラのログで確認した。
23 はチャンクがキューボイド形式で、ダイレクトセルでは
ログイン直後のキューボイドチャンク群をフロントエンド
越しに読み切ってから Keep Alive に到達しており、チャンク
到達と無切断も裏付けられた。ブリッジセルでは 1.7.10 の
セクション形式チャンクがキューボイドへ再配置されて
23 クライアントへ届く経路を通した。回帰 115 セルと
合わせて **統合 127 セルすべて合格**、分割検証は
**4,998 件・合格 4,981・失敗 0・スキップ 17**、最終監査
も合格。リベースの競合と重複解消の経緯は
docs/PROXY-1.2.3.md の Stage E 節を参照。

1.1 のログ形式は実バニラ 1.1 の server.log で実測したとおり
1.2 世代と同じ形（旧接頭辞＋名前とアドレスの間に空白が
ある「logged in」行）で、既存の VanillaLogParser のまま
参加・チャットを読み取れた（パーサー変更は不要で、
ダイレクトセルがそれを実証した）。

**Stage E で見つけた実バグ：なし**。ブリッジ fake23 セルは
初回実行でログイン応答タイムアウトにより失敗したが、
単独再実行で合格した（既知の環境フレーク。初回失敗 XML は
`split-verification-28/cell40-first-failure.xml` に保持）。

本物の 1.1 ゲームクライアントでの確認は未実施。
ブリッジモードでアイテム実体を 0x17 種別 2 で送る方式の
実クライアント受け可否も未確認のまま
（`docs/PLAYTEST-1.1.md` の最重点項目）。
