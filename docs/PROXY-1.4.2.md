# 旧プロトコル47（Minecraft 1.4.2）対応ノート

DetergentMC のレガシーフロントエンド（`detergentmc-legacy-frontend`）が旧プロトコル47
（**1.4.2**）を受けられるようにした記録。Stage A の実測が正であり、
本文書の数値はすべて実 jar・実バニラからの採取に基づく。

⚠️ **番号の衝突について**：「47」には2つの意味がある。Netty 世代のプロトコル47は
**1.8 系**（プロキシ本体側で対応済み）であり、本書の対象である旧プロトコル47
（**1.4.2**、Netty 以前世代）とは別物である。旧47 は legacy モジュール内にのみ
置き、`ProtocolVersion` には入れない。コード・設定・ドキュメントでは
「旧プロトコル47（1.4.2）」と「プロトコル47（1.8）」を常に書き分ける。

## Stage A：実測（1.4.2 サーバー jar、JDK 8）

- バニラ 1.4.2 サーバー jar SHA-1 `5be700523a729bb78ef99206fb480a63dcd09825`
  （piston-meta 照合済み。先行調査 `legacy-prep-old/PREP-OLD.md` の
  レガシーピング §1＋ハンドシェイク探測の実測とも一致）。
- パケット登録は jar から機械抽出（基底クラス `dx`）。**登録 75 件**。
- 49⇔旧47 の差分は次のとおり（49＝1.4.5 の機械抽出との全件比較）。
  51⇔49 の差分よりさらに小さく、**ワイヤ形式の差分はゼロ**：
  1. **登録 ID 集合・方向フラグ・全 75 件の読み書きスキーマが 49 と完全一致**。
     49 の特徴は旧47 にもすべて存在する：0x15 pickup_spawn あり、
     0x17 spawn_object に回転バイト無し、0x64 open_window に useTitle 無し、
     0x10 held_item_change はサーバー行きのみ、0x04 time は I64×2、
     0x08 体力 I16、0xC8 amount I8、0xCA 速度バイト（値/255）。
  2. **チャンクバルク 0x38 に skyLight フラグは無い**（旧47 の jar の
     読み取り列でも [I16 件数, I32 長, データ, チャンクごと I32/I32/I16/I16]
     で BOOL が存在しないことを確認。フラグは 51 から、という 49 の
     実測が旧47 でもそのまま成り立つ）。単体チャンク 0x33 も 49 と同形。
  3. 補助形式も 49 と同一：DataWatcher（クラス `lt` の static 読み）は
     tableswitch 0〜6 の **7 型**・終端 0x7F。スロット読み（基底クラス
     `dx.c`）は I16 id＋U8 個数＋I16 ダメージ＋NBT（I16 長＋gzip 圧縮、
     `br.a` 経由）で、49 と同形。
- レジストリ差分（両 jar の Block/Item 登録名対応とエンティティ登録の機械比較）：
  - **ブロックは完全同一**（登録名 121 件、ID 対応も差分なし）。
  - **アイテムは 1 件だけ差分**：ID 2267 のレコード（ディスク "wait"）が
    旧47 に無い（1.4.4 で追加。旧47 のディスクは 2256〜2266 の 11 枚）。
    削除・変更は無し。なお 2267 は **1.6.4 の jar のアイテムレジストリにも
    `record_wait` として存在する**ことを今回あわせて実測した（後述の
    78 層の訂正の根拠）。
  - **エンティティは完全同一**（登録 48 件、名前・ID とも一致。
    花火ロケット（オブジェクト種別 22）は 49・旧47 のどちらにも無い）。
- 実ワイヤ採取（実バニラ 1.4.2、暗号化ログイン＋歩行＋チャット）：
  148 パケットを末尾までズレなく解析（オフライン再解析でも
  ストリームをちょうど消費）。チャンクバルク 89 件（チャンク 441 個）の
  全件で、膨張後サイズが Σ（セクション数×10240＋追加配列×2048＋256）と
  一致し、**フラグバイトがワイヤに無い**形で解析が通った（空光配列は
  ペイロード内にあり、次元から有無が決まる。49 と同じ）。
  チャットはサーバーログに到達。プロトコルエラー・切断なし。
- pack_format の概念はこの世代に無い（テクスチャパック）。
  DataVersion の概念も無い。

## 近似・落とすもの（旧47 向け）

- レコード 2267（"wait"）→ レコード 2266（"11"）に近似する
  （"wait" は "11" の修正版ディスクであり、旧47 に存在する最も近い
  ディスク。49 層の後に適用する旧47 専用の 1 件だけのアイテム層）。
- **ついでに直した既存の誤り**：78 層（`LegacyChunkRemap.itemId5To78`）には
  「2267 は 1.7 のディスク」という誤った前提で全レガシー世代向けに
  2267→2256（"13"）へ写す特別扱いがあった。今回の実測（1.6.4 と
  1.4.5 の jar のアイテムレジストリ抽出）で 2267 は 1.4.4 の追加であり
  1.4.2 以外の全レガシー世代に存在すると確定したため、特別扱いを
  撤去し、近似は旧47 層の 1 件だけに移した。78〜49 向けの挙動が
  この 1 アイテムについて変わる（"wait" が "wait" のまま届くように
  なる）が、これは実測に基づく訂正であり、固定していた単体テストも
  あわせて更新した。
- ブロック・その他のアイテム・エンティティは 49 と完全同一なので、
  近似はすべて 49 層（→51 層→…）をそのまま使う。
- 49 世代と共通の制限はそのまま継承する：スコアボードと
  名前付きパーティクルは無い、体力は I16 へ丸め、能力速度は
  バイト量子化、馬はブタ、属性／乗り物操作は無い、
  花火ロケットのスポーンは落とす。

## 実装（Stage B〜D、2026-11-20）

ワイヤ差分ゼロの帰結として、実装は最小の追加で済んだ。

- `LegacyProtocol`：定数 `V1_4_2`（= 47、レガシー番号空間）を追加。
  対応レガシー一覧は [78, 74, 73, 61, 60, 51, 49, 47] に固定。
  版名 "1.4.2" ⇔ 旧47 の対応、`is1_4Generation` への旧47 の追加、
  花火ロケット不在の判定（`hasNoFireworkRocket`）は 49 と旧47。
- `LegacyPacketTable`：旧47 の表は 49 の表への**全面委譲**
  （`V1_4_2 = V1_4_5`）。新規コーデックはゼロ。
- `LegacyChunkRemap`：旧47 専用のアイテム層を 1 件だけ追加
  （2267→2266）。ブロックは 49 へ全面委譲。あわせて 78 層の
  2267 特別扱いの誤りを訂正（近似・落とすものの節を参照）。
- `LegacyPlayTranslator`：スロット変換のディスパッチに旧47 の
  分岐を追加。花火ロケットの落としは 49 と共通の判定に統合。
- アダプタ：`V1_4_2Adapter`（ブロック集合は `since` ≤ 1.4.2。
  代表集合では 1.4.5 と同一）を legacy モジュールに追加し
  ServiceLoader に登録。コア側は `minecraft-version: 1.4.2` で
  ダイレクトモード配線（`LegacyWiringTest`）、内部バニラの
  Java 8 対象に "1.4.2" を追加、versionedJars の版リストに
  '1.4.2' を追加。
- 単体テスト：表の固定（旧47＝49 の全件一致を含む）、
  コーデック往復、変換器、E2E（ダイレクト中継・ブリッジの
  0x85／0x2C 落とし・§1 ピング 47 / 1.4.2）、アダプタ・配線
  テストを追加。分割検証の総数は docs/VERSIONS.md の
  旧47節を参照。

## Stage E：実バニラ統合（完了）

- 51／49 の Stage E 最終 HEAD `6332e38` へ旧47のコミットを
  リベース（競合は docs/VERSIONS.md のみ、両側を保持して
  解決）した上で実施。先行世代の Stage E 修正（旧ログ接頭辞、
  暗号化ハンドシェイク順序、0xCD Client Status、onGround の
  BOOL 化、ピング §1 の完全形仕様、VanillaLogParser の
  「logged in」行対応）はすべて取り込み済み。
- 新規セル 3 件（LegacyFrontendIntegrationTest）：
  ブリッジ fake旧47 → 実バニラ 1.7.10、ダイレクト fake旧47 →
  実バニラ 1.4.2（暗号化ログイン込み）、§1 ピング（完全形）。
  参加系は参加→チャット→Keep Alive 応答→応答後の2通目の
  チャット到達を実バニラのログで確認。**3 件すべて合格**。
- 回帰は 51／49 の Stage E の全 102 セル（Netty 77＋レガシー
  25）をそのまま実行し、**統合は合計 105 セルすべて合格**。
  分割検証は **4,851 件（合格 4,834・失敗 0・エラー 0・
  スキップ 17）**、最終監査（全クラスの XML 実在＋全統合
  セルのメソッド名一致）も合格。
- 初回失敗の記録（いずれも再実行で合格し、環境要因と確定）：
  Netty セル 0・2・3 が VM 再起動直後の負荷で Login Success
  タイムアウト、セル 48 がポート競合（BindException）。
  初回失敗の XML は split-verification-47old/ の
  cell*-first-failure.xml に証拠として残してある。
- **Stage E で直した実バグ（39 の作業からの申し送り）**：
  DataWatcher のスロット型（メタデータ種別 5）は旧47 では
  **NBT 無し（id・個数・ダメージのみ）**が正しい（39 の実装時
  に 1.4.2 の実 jar で実測。完全形の到着は 1.4.4）。本ツリーは
  39 の子孫ではなく 49 の系統だったため、この修正が入って
  おらず、フロントエンドは旧47 のメタデータを完全形で読み
  書きしていた。Stage E で同等の修正を移植
  （`LegacyProtocol.watcherSlotHasNoNbt`、LegacyWire の
  plain 形式リーダー／ライター、PacketIO の選択、
  変換器側の空エントリ落とし）し、バイト列で固定する単体
  テスト（`watcherSlot47OldCarriesNoNbt`）を追加した。
  なお通常スロット（0x67／0x68 等）の読みは完全形のままで
  正しい（Stage A 実測どおり）。ダイレクトセルの実トラフィック
  では、参加直後のバニラ送信にメタデータ系パケット（0x18／
  0x28）自体が現れなかった（Stage A の採取 148 パケットでも
  同様）ため、スロット入りメタデータの実地解析は観測できて
  いない。解析の正しさは jar 実測＋単体テストで固定し、
  実地の裏付けは今後の課題として残す。

## 検証の範囲と残る制限

- Stage A〜E まで完了。Stage A の裏付けは jar 機械抽出＋
  実バニラ 1.4.2 への採取セッション 1 回（暗号化ログイン＋
  歩行＋チャット、148 パケット完全解析）まで。
- **本物の 1.4.2 ゲームクライアントでの確認は未実施**。
  特にブリッジモードでアイテム実体を 0x17 種別 2 で送る方式が
  実クライアントで表示できるかは 49 世代から引き継いだ
  未確認点（docs/PLAYTEST-1.4.2.md の最重点項目）。
- 旧世代は offline 前提（Mojang の旧認証エンドポイントが
  廃止されているため）。ブリッジモードはコアの
  offline-mode が前提。
- 49 世代と共通の制限（スコアボード・名前付きパーティクル
  無し、体力 I16、能力速度のバイト量子化、馬→豚、属性・
  乗り物操作無し、統計はブリッジでは届かない、花火ロケット
  のスポーンは落とす、1.5 追加分の近似）はすべて継承する。
