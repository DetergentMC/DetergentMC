# DetergentMC 1.21／1.21.1 実機プレイテスト — チェックリスト

2026-11-10作成。1.21／1.21.1クライアント（プロトコル767）で1.20系・
1.21系サーバーに参加する実機確認のための手順と、結果の記録用。既存の
`PLAYTEST-1.20.1.md`（1.20.1クライアント用）・`PLAYTEST-1.20.2.md`
（1.20.2クライアント用）・`PLAYTEST-1.20.4.md`（1.20.4クライアント用）・
`PLAYTEST-1.20.5.md`（1.20.5／1.20.6クライアント用）は直接いじらず、
こちらを1.21／1.21.1専用の手順書とする。

## 0. この手順書の読み方：プロトコル検証済み／実機でしか確認できないもの

DetergentMCの1.21／1.21.1対応は、ここに書く項目の多くを**プロトコルレベルでは
すでに検証済み**である（本物のバニラ子プロセス＋生ソケットで767クライアントを
装った統合テスト `ProxyIntegrationTest`、`ProxySession767Test`、
`ChunkTranslator767Test` など）。実機テストの目的は、プロトコルレベルでは見えない
「本物のゲームクライアントでの見た目・挙動」を確かめることである。以下の2つに
分けて読むこと。

### A. プロトコルレベルで既に検証済みの項目（実機では「同じことが起きるか」の確認）

- 767クライアントの1.21サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake767ClientJoinsRealVanilla121ThroughProxy`）。
  素通し（リレー）
- 767クライアントの1.21.1サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake767ClientJoinsRealVanilla1211ThroughProxy`）。
  素通し（リレー）
- 767クライアントの1.20.5サーバー（内部766）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake767ClientJoinsRealVanilla1205ThroughProxy`）。
  設定フェーズは766の Registry Data を767の順序に並べ替えて中継する
- 766クライアントの1.21サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake766ClientJoinsRealVanilla121ThroughProxy`）。
  設定フェーズは767の Registry Data を766の順序に並べ替えて中継する
  （jukebox_song は落とす）
- 767クライアントの1.20.4サーバー（内部765）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake767ClientJoinsRealVanilla1204ThroughProxy`）
- 765クライアントの1.21サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake765ClientJoinsRealVanilla121ThroughProxy`）
- 767クライアントの1.20.2サーバー（内部764）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake767ClientJoinsRealVanilla1202ThroughProxy`）
- 764クライアントの1.21サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake764ClientJoinsRealVanilla121ThroughProxy`）
- 763クライアントの1.21サーバー（内部767）への参加・スポーン・移動・チャット
  （`ProxyIntegrationTest.fake763ClientJoinsRealVanilla121ThroughProxy`）。
  プロキシが Join Game の codec から Registry Data（767形式 0x07）と
  Finish Configuration を合成して送る
- 本物のバニラ1.21／1.20.5から Registry Data の順番を記録するテスト
  （`RegistryOrderCaptureTest`）。エンチャントのアルファベット順、
  絵画50件の順番、旗の模様43件、トリム18件、ダメージ種別47件、
  ジュークボックスの歌19件を確認済み。1.20.5の絵画30件の順番は
  ViaVersion mapping-1.20.5.json で確認済み（1.20.5は絵画を
  Registry Data で送らないため、実サーバーの Registry Data では
  確認できない）
- `/trigger d_hello` / `d_lang_ja` / `d_lang_en` の動作（言語切替と保存を含む。
  1.20.4サーバーでの検証を流用）
- サーバーリストのpingでバージョンが **1.21**（protocol 767）と表示されること
  （`ClientAdapter767Test`）
- 767クライアントへのリソースパックのオファー：設定フェーズの Add Resource Pack
  （0x09、UUID付き）に、URLとSHA-1が **767用パック（pack_format 34、
  `detergentmc-pack-1.21.zip`）** のものであること。クライアントの応答
  （設定 0x06・プレイ 0x2B）はバニラのパックのUUID付きでバニラへ返されること
  （`ProxySession767Test`）
- 767用パックのzip内容：`pack.mcmeta` が `pack_format: 34` で、泡テクスチャ
  （16x16 PNG）・泡モデル・スライムボールのオーバーライドが入っていること
  （`ResourcePackBuilder767Test`）
- 767用パックと763用・764用・765用・766用パックの配信：同じ25567番ポートで5つの
  URLが200を返し、SHA-1が一致すること（`ResourcePackServer767Test`、
  `ResourcePackWiringTest`）
- 767＋online-modeの認証：プロキシがMojang認証を完結させ、認証済みUUID・名前で
  内部バニラへ繋ぐこと（`ProxySession767Test`、偽セッションサーバーでの検証）。
  認証失敗時は理由付きLogin Disconnectで切断されること
- 766↔767対応表（逆向きは反転）と763↔767・764↔767・765↔767の合成表
  （`RegistryRemapper767Test`、検証スクリプト
  `detergentmc-protocol/tools/verify-767-tables.py` 9群のチェックと
  `verify-reverse-tables.py`）
- 内部767サーバーの配線：`ClientProxy` が内部767で構築できること
  （`ClientProxy767Test`）、`DetergentServer` が
  `minecraft-version: "1.21"`／`"1.21.1"` のときに内部767・767用パックの
  差し替え・767用パックのバニラ渡しをすること
  （`ServerProtocolWiringTest`）

### B. 実機でしか確認できない項目（この手順書の本題）

- リソースパックがクライアントの画面で「互換性あり」と表示され、実際に
  ダウンロード・適用されること（プロトコル検証では、クライアントがパックを
  受け取って適用したかどうかまでは見えない）
- 泡テクスチャが**目で見て**泡に見えること（スライムボールが泡の絵になるか）
- スポーン地点の風景・チャンク・ブロックが正しく表示されること
  （1.21で追加された音楽ディスク3曲・新絵画20件は、古いサーバーでは
  落とされるか代替表示される。目で見て確認する）
- 次元移動（ネザー／エンド）で画面に何が起きるか（Respawn は767で
  dimension 番号のため変換する。実機で正しく切り替わるか確認する）
- レシピ帳が空になること（Declare Recipes を落としているため。実機での
  見た目を記録する）
- インベントリ操作ができるか（Window Click／Set Creative Slot は
  767→763／764／765では変換できず落としている。**古いサーバーでは
  インベントリ操作ができない既知の制限**。766サーバーとのあいだでは
  変換できる。実機でどこまで操作できるか記録する）
- トライアルチャンバー（トライアルスポナー・vault・銅の電球）が
  1.21サーバーで正しく表示・動作すること（1.21の顔である新要素）
- 1.21の新要素（ブリーズ・ウィンドチャージ・メイス・オオカミの鎧・
  アルマジロ）が1.21サーバーで正しく表示・動作すること
- online-modeでのMojang認証の成否（実アカウントが必要。下の「5. online-mode」を参照）
- 体感の遅延・切断の有無、スキンの表示、サウンドなど

## 1. 起動

### 1.1 準備（初回のみ）

```sh
cd ~/workspace/detergentmc
./gradlew build :bubbles:hello-bubble:jar
cp bubbles/hello-bubble/build/libs/hello-bubble-0.1.0-1.20.4.jar run/bubbles/
```

`run/eula.txt` と `run/vanilla/eula.txt` が `eula=true` になっていること。

### 1.2 起動（ファットjar・推奨）

```sh
java -Dfile.encoding=UTF-8 -jar build/libs/detergentmc-0.1.0-1.20.4.jar
```

Gradle経由の `./gradlew :detergentmc-core:runServer` ではコンソール入力が
届かないので、対話するなら上の `java -jar` で起動すること。

起動完了の目安：`Done (...)!` と `バニラサーバーが起動しました (ポート 25565)。`

この手順書の参加テストでは、サーバーはまず **1.21** のまま
（`minecraft-version: "1.21"`、既定ではないため設定で変える。下の「1.5」を参照）
で、1.21／1.21.1クライアントがプロキシ経由で参加する。サーバー自体を
1.20系で動かす場合は下の「1.5 サーバーを別バージョンで動かす場合」を参照すること。

### 1.3 ポート構成

| ポート | 既定 | 役割 |
| --- | --- | --- |
| `server.port` | 25565 | プロキシの公開ポート。**クライアントは必ずここに接続する** |
| `server.internal-port` | 25566 | バニラの待ち受けポート（`127.0.0.1` のみ。直接つながないこと） |
| `resource-pack.port` | 25567 | リソースパック配信用（loopbackのみ）。765用・763用・764用・766用・767用の5つを出す |

起動時に5つのパックが生成される：

| ファイル | 中身 |
| --- | --- |
| `run/data/resource-pack/detergentmc-pack.zip` | 765用（pack_format 22）。`server.properties` の `resource-pack` に書かれる（内部765のとき） |
| `run/data/resource-pack/detergentmc-pack-1.20.1.zip` | 763用（pack_format 15）。プロキシが763クライアントにだけ出す |
| `run/data/resource-pack/detergentmc-pack-1.20.2.zip` | 764用（pack_format 18）。プロキシが764クライアントにだけ出す |
| `run/data/resource-pack/detergentmc-pack-1.20.5.zip` | 766用（pack_format 32、1.20.5と1.20.6で共用）。プロキシが766クライアントにだけ出す |
| `run/data/resource-pack/detergentmc-pack-1.21.zip` | 767用（pack_format 34、1.21と1.21.1で共用）。プロキシが767クライアントにだけ出す |

コンソールに `リソースパックを配信しています: http://127.0.0.1:25567/detergentmc-pack.zip`
が出れば配信開始。767用パックも同じポートの
`http://127.0.0.1:25567/detergentmc-pack-1.21.zip` で配信される。

### 1.4 online-mode／offline-modeの切替方法

`run/detergentmc.yml` の `server.online-mode` を変える。既定は `true`
（プロキシがMojang認証を完結させる）。実機で正規アカウントを使わない
確認（オフラインの動作確認だけ）なら `false` にする。内部バニラは常に
offline-mode（信頼済み接続）で動くため、ここの切替はプロキシ認証の
オン／オフである。

```yaml
server:
  online-mode: false
```

### 1.5 サーバーを別バージョンで動かす場合

`run/detergentmc.yml` の `minecraft-version` を変えて再起動する。
内部プロトコル・データパック形式・バニラに渡すリソースパックが連動して変わる。

| `minecraft-version` | 内部プロトコル | データパック | バニラに渡すリソースパック | 注意 |
| --- | --- | --- | --- | --- |
| `1.20` / `1.20.1` | 763 | 15 | 763用（pack_format 15） | プロキシが767クライアントの設定フェーズを合成する |
| `1.20.2` | 764 | 18 | 764用（pack_format 18） | 設定フェーズは767形式へ変換して中継する |
| `1.20.3` / `1.20.4` | 765 | 26 | 765用（pack_format 22） | 設定フェーズは767形式へ変換して中継する |
| `1.20.5` / `1.20.6` | 766 | 41 | 766用（pack_format 32） | **Java 21 が必要** |
| `1.21` / `1.21.1` | 767 | 48 | 767用（pack_format 34） | **Java 21 が必要**（下の注意を参照） |

#### Java 21 の注意（1.20.5／1.20.6／1.21／1.21.1サーバーのときだけ）

バニラ1.21／1.21.1サーバーは Java 21 を要求する。DetergentMC本体は
Java 17 で動く。`VanillaServerHost` は次の順番で Java 21 を探す。

1. `detergentmc.java21.home` システムプロパティ、
2. `DETERGENTMC_JAVA21_HOME` 環境変数、
3. 現在の `java.home` が Java 21 以上のときはそれ、
4. どれも無いときは現在の Java を使うが、バニラが起動を拒否する。

ファットjarを Java 17 で起動したまま、内部だけ Java 21 にする例：

```sh
DETERGENTMC_JAVA21_HOME=$HOME/workspace/.tools/jdk-21.0.13+9 \
  java -Dfile.encoding=UTF-8 -jar build/libs/detergentmc-0.1.0-1.20.4.jar
```

ファットjar自体を Java 21 で起動してもかまいません（その場合は3. の経路）。

## 2. 参加（1.21／1.21.1クライアント）

1. Minecraft 1.21 または 1.21.1 のクライアントを起動する。
2. マルチプレイ → サーバーを追加 → アドレスに `127.0.0.1:25565`
   （`server.port` の既定。直接つなぐ内部ポート 25566 ではないこと）。
3. サーバーリストでバージョンが **1.21**（protocol 767）と表示されること。
4. サーバーに参加する。リソースパックのオファーが出たら承諾する
   （pack_format 34 の767用パック）。
5. スポーンしたら、チャットで何か打ってみる（バニラログに
   `<名前> メッセージ` が出ること）。

## 4. わざと失敗するはずのもの（バグではない）

- 1.21.2以降のクライアント（プロトコル768以上）はログイン時に断られる
  （「新しすぎます」）。
- 1.20.1より古いクライアント（プロトコル762以下）はログイン時に断られる
  （「古すぎます」）。
- 古いサーバー（内部763／764／765）での Window Click／Set Creative Slot は
  落とされる（上の「3.7」を参照）。バグではなく、データコンポーネント形式と
  NBT 形式の変換が未実装のため。
- 内部763／764／765のサーバーで、1.21の新要素（新絵画・新音楽ディスクなど）は
  表示されないか代替表示になる（対応表で落とすか近いものへ変えるため）。
