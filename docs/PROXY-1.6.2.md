# プロトコル74（Minecraft 1.6.2）— Netty 以前世代フロントエンド

DetergentMC の Netty 以前世代フロントエンド（モジュール
`detergentmc-legacy-frontend`、docs/PROXY-1.6.4.md）の第2弾。
レガシープロトコル 74（1.6.2）を 78（1.6.4）と同じ基盤に追加する。

**状態：Stage E 完了（2026-11-20）。実バニラ統合セル全合格。**
**本物の 1.6.2 クライアントでの確認は未実施。**

## 番号の規律

78 と同じ規律（docs/PROXY-1.6.4.md）：旧世代の番号は legacy
モジュール内にだけ置き、`ProtocolVersion` / `PacketIds` には
足さない。対応一覧は分けて数える。

## Stage A で実測確定した事項（2026-11-20）

土台：実バニラ 1.6.2 サーバー jar（piston-meta から取得、SHA-1
`01b6ea555c6978e6713e2a2dfd7fe19b1449ca54` を再検証）を JDK 8 で
起動し、jar のバイトコード解析＋実ワイヤ採取（スポーン有効・
歩行あり）の両方で確定した。クライアント jar も piston-meta から
取得し SHA-1 `b6cb68afde1d9cf4a20cbf27fa90d0828bf440a4` を照合した。

### 結論：78⇔74 のワイヤ差分はゼロ

- **パケット登録**：1.6.2 の jar から 78 と同じ機械抽出手順
  （基底パケットクラスの静的初期化子にある登録呼び出し＋各
  パケットクラスの read／write メソッドの呼び出し列抽出）で
  取り直した結果、**登録は 82 件、ID 集合・方向フラグとも
  78 と完全一致**した。抽出器自体の正しさは、同じ抽出器で
  1.6.4 を取り直して 78 の登録記録（registrations.json）と
  全件一致することで裏付けた。
- **パケット形式**：82 件全てについて、read メソッドと write
  メソッドの呼び出し列が、難読化されたクラス名の差を正規化
  すれば **78 と完全一致**した。委譲先ヘルパーの内部も個別に
  比較し一致を確認した：DataWatcher（entityMetadata）の
  読み書き、移動パケットの共有ヘルパー、基底クラスの文字列
  読み・バイト列読み・スロット読み、ItemStack の呼び出し集合。
  - チャンクバルク 0x38 のヘッダは 78 と同形で、圧縮長の直後に
    **skyLight フラグ（bool）がある**（51〜78 の形。39 には無い）。
  - entityMetadata は型7種・終端 0x7F、スロット NBT は gzip、
    移動パケットの順序 [x, stance, feetY, z]、テクスチャパックは
    MC|TPack — いずれも 78 の確定事項がそのまま成り立つ。
- **レジストリ差分：なし**。クライアント jar の lang キーを
  1.6.4 と比較し、tile（232）・item（211）・entity（49）の
  キー集合が完全一致した。lang 全体の差分は 1.6.4 で追加された
  サーバーコマンド名（setidletimeout）だけで、ワイヤには無関係。
  → `LegacyChunkRemap` の近似表（1.7 追加分のブロック／アイテム）
  は 74 でもそのまま使える。
- **実ワイヤ採取**：実バニラ 1.6.2（offline、FLAT、スポーン
  有効）へ暗号化ログイン（プロトコル 74）し、歩行＋チャット＋
  Keep Alive 応答を行った採取を、78 由来の表で **698 パケット
  すべて末尾まで完全解析（ズレ0）**した。チャットはバニラの
  ログに到達し、プロトコルエラーは無かった。ログイン直後の
  MC|Brand プラグインメッセージも 74 で届くことを確認した。
- **レガシーピング**：§1 形式（`§1␀74␀1.6.2␀…`）。素の FE01 と
  完全形（PingHost 付き）の両方で §1 を返す（先行調査で実測。
  73 のような癖は無い）。

### したがって実装方針は

74 のパケット表は 78 の表への **全面委譲（同一レイアウト）** とし、
差分として実装するのはプロトコル番号の配線だけ：

- `LegacyProtocol` に V1_6_2（=74）を追加し、対応一覧に含める。
- セッションはハンドシェイクのプロトコル番号で 78／74 を
  受け分ける（ログイン列・暗号化は共通）。
- ダイレクトモードは内部サーバー 1.6.2 へプロトコル 74 で
  ログインする。クライアントとバックエンドのプロトコルが
  異なる場合はバニラと同じく蹴る。
- アダプタ（V1_6_2Adapter）と内部サーバーの Java 8 配線、
  versionedJars への 1.6.2 追加。

## 実装（Stage B〜D、2026-11-20）

- `LegacyProtocol`：V1_6_2（=74）を追加。対応一覧は [78, 74]。
  バージョン名⇔プロトコルの相互変換もここに置く。
- `LegacyPacketTable.V1_6_2` は 78 の表への全面委譲（同一
  インスタンス）。将来 74 だけが変わることがあればここを
  実体化する。
- コーデックのプロトコル引数化：`LegacyPacketIO.parseOne／
  write`、`StreamParser`、`LegacyConnection` がプロトコルを
  保持し、セッションはハンドシェイクで判明した番号へ付け
  替える（バッファ済みバイトは失わない）。ログイン列・暗号化・
  変換器は 78 と共通のまま。
- セッション：対応プロトコルなら受け入れ、外れたら番号の
  大小で "Outdated client!"／"Outdated server!" を返す。
  ダイレクトモードではクライアントとバックエンドの
  プロトコル不一致もバニラと同じ文言で蹴る。
- ピング：設定のバージョン名に対応するプロトコル番号で §1 を
  返す（ダイレクト 1.6.2 構成では 74 / "1.6.2"）。
- バックエンド面：`LegacyBackendLogin` がプロトコル引数を取り、
  ハンドシェイク（u8）とログイン（i32）にその番号を書く。
- アダプタ：`V1_6_2Adapter`（ブロック集合は 1.6.4 と同一）を
  META-INF/services に登録。コア側は `VanillaServerHost` の
  Java 8 対象に 1.6.2 を追加し、`legacyConfig` が
  minecraft-version をダイレクト設定へ渡す。versionedJars に
  1.6.2 を追加。
- 単体テスト：レガシーモジュール 69 件（74 用に +8）を含む
  分割検証を実施（集計は split-verification-74/ と Stage D
  コミットを参照）。

応答後の 2 通目のチャット到達までを実バニラのログで確認
