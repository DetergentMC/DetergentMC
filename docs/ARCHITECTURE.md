## 設計の決まりごと

1. **APIはバージョンを知らない。** `detergentmc-api` はどのモジュールにも依存しない。
   バブルはこのAPIだけを使って書く。だから、あるバージョン向けに書いたバブルが、
   別のバージョンでも（アダプターさえあれば）動く。
2. **バージョンの違いはアダプターに閉じ込める。** 1バージョン＝1モジュール。
   アダプターは `VersionAdapter` を実装し、`META-INF/services` で登録する。
   コアは ServiceLoader で見つけて、`detergentmc.yml` の `minecraft-version` に
   合うものを選ぶ。コアは特定バージョンに依存しない（`runtimeOnly`）。
3. **プラグインは「バブル」と呼ぶ。** 1つの拡張機能＝1つのバブル。1つのjarに
   `bubble.yml`（id・名前・バージョン・説明・作者・mainクラス・依存関係）を入れる。
   ローダーは `bubbles/` のjarを読み、`depends` の順に有効化する。依存が欠けていたり
   循環していたりしたら、起動時に分かりやすいエラーで止まる。
4. **言葉は言語ファイルで管理する。** `locales/ja.yml` / `locales/en.yml`。
   翻訳の検索順は「要求された言語 → 標準言語（フォールバック）→ キーそのもの」。
   翻訳がなくても落ちない。サーバーの標準言語とプレイヤーごとの言語は別にできる。
5. **MojangのコードもPaperのコードも含めない。** 土台はバニラだが、バニラjarは
   リポジトリに入れず、ビルド時・実行時にMojang公式から取得する形にする。
   アダプターの本物のNMS結合は、公式Mojangマッピングを使って行う（TODO）。

## バブルのライフサイクル

1. `BubbleLoader` が `bubbles/*.jar` を見つけ、`bubble.yml` を読む。
2. `depends` をトポロジカルソートし、依存関係の順に有効化する。
3. 各バブルに `BubbleContext`（設定・翻訳・イベント・コマンド・サーバー・データフォルダ）を渡して `onEnable` を呼ぶ。
4. 終了時は逆順に `onDisable` を呼び、クラスローダーを閉じる。

## 多言語の仕組み

- 言語ファイルは `locales/<言語>.yml`（例：`ja.yml`、`en.yml`）。
- サーバーの `locales/` に置いたファイルが、jar内蔵のものを上書きする（運営者の上書き用）。
- `Translator.translate(key, locale, args)` は `java.text.MessageFormat` 形式（`{0}`）を使う。
- 未翻訳のキーは、標準言語の文言を表示する。それもなければキーそのものを返す。

## 古いクライアントへの対応（設計）

- **ブロック変換**：`SimpleBlockTranslator` が「サーバー側ブロック → クライアントに見せるブロック」の
  対応表を持つ。例：1.12.2のクライアントには `cherry_log` の代わりに `oak_log` を送る。
- **テクスチャ**：`ResourcePack` でリソースパックを配り、見た目を補う。
  カスタムブロック（`CustomBlock`）は「土台ブロック＋テクスチャ＋表示名キー」で定義する。
  配信は2通りある。既定はloopback配信（`ResourcePackBuilder` で生成し、
  `ResourcePackServer` が `127.0.0.1` でHTTP配信）。`detergentmc.yml` の
  `resource-pack.url` に `https://` のURLを書くと外部配信になり、ローカル配信は
  行わず、設定のURL・SHA-1をそのまま `server.properties` に書き込む。
  `http://` は拒否してloopbackに切り替わる。外部パックのSHA-1は形（40桁の16進数）
  だけを検証し、ホストされたファイルとの照合はしない（ホスト側のファイルが
  ローカルのデモパックと違っていてもよいため。合わなければクライアント側で拒否される）。
  公開HTTPSの置き場所はまだ未定で、決まるまでは既定のloopbackのまま。
  くわしくは `ResourcePackMode` のjavadocとREADMEの「リソースパックのデモ」を参照。
- **UI**：`CustomUI` はタイトルキーとスロット数で定義する。描画方法はクライアントの世代で変える。
- **クライアントアダプター**：`ClientAdapter` が違うバージョンのクライアントが
  参加するときの判断をする。方針は「変換はクライアントとの境界面だけで行う」。
  内部プロトコルは `minecraft-version` で決まる（1.20.1サーバーなら763、
  1.20.2サーバーなら764、1.20.4サーバーなら765、1.20.5／1.20.6サーバーなら766、
  1.21／1.21.1サーバーなら767）。

### 設定フェーズ消費とJoin Game変換の流れ（763）

1. ハンドシェイクのプロトコルVarIntを763→765に書き換えてバニラへ送る。
2. Login Startは763形式（UUIDの有無を示すbool付き）から765形式に変換する。
   UUIDが無い場合は offline UUID v3（`"OfflinePlayer:"+名前` のMD5）を合成する。
3. ログイン成功後、プロキシが765クライアント役として設定フェーズを消費する。
   Login AcknowledgedとClient Informationをバニラへ合成して送り、
   Registry Dataを受け取って保持し、Finish Configurationを受けたら
   Acknowledge Finish Configurationを返す。
4. バニラが送るJoin Game（765の0x29）を763向けJoin Game（0x28）に変換する。
   763形式にはdimension codec（NBT）が必要で、保持した
   `minecraft:dimension_type` と `minecraft:worldgen/biome` の
   レジストリから組み立てる。
5. スポーンは763式。Spawn Position（0x50）が合図で、765のGame Event 13は
   763クライアントに送らない。

### 設定フェーズ中継とJoin Game素通しの流れ（764）

763と違い、764には設定フェーズがあるため、プロキシは設定フェーズを
消費しない。流れは次の通り。

1. ハンドシェイクのプロトコルVarIntを764→765に書き換えてバニラへ送る。
2. Login Startは765と同形式（名前＋UUID、bool なし）のため変換しない。
3. ログイン成功後、クライアントが Login Acknowledged（0x03）を送ると
   両方とも設定フェーズに入る。Registry Data は765と同じ1個の名前なし
   NBT codec のためそのまま通す（内容はプロキシも保持する）。
   Add Resource Pack は764の設定フェーズの Resource Pack Send
   （0x06、UUIDなし）に変換する。Tags はレジストリ番号がずれるため落とす。
4. Finish Configuration（0x02）を中継し、クライアントの応答（0x02）が
   バニラに届いた時点で両方ともプレイ状態に入る。
5. バニラが送るJoin Game（0x29）は764でも同じ0x29・同形式のため変換なし
   で通す。763のような codec の埋め込みは不要。
6. スポーンは764式。Spawn Position（0x52）が合図で、765のGame Event 13は
   764クライアントに送らない。

プレイ中の Start Configuration も764にあるためそのまま中継する
（763のような肩代わりはしない）。レジストリ番号の変換は763向け表とは
別の764用対応表（`RegistryRemapper` の `*_764` の表と
`ChunkTranslator` の `*765To764` メソッド）を使う。763向け表と764向け表は
ブロック状態17,104件・音245件が異なるため、763向け変換の流用では
誤変換になる。くわしくは `docs/PROXY-1.20.2.md` を参照。

### 逆向き（内部764）の流れ（765クライアント）

`minecraft-version: "1.20.2"` でサーバー自体が1.20.2（内部764）のとき、
765クライアントは下向き変換で参加する。流れは次の通り。

1. ハンドシェイクのプロトコルVarIntを765→764に書き換えてバニラへ送る。
2. Login Startは765と764で同形式（名前＋UUID）のため変換しない。
3. ログイン成功後、クライアントが Login Acknowledged（0x03）を送ると
   両方とも設定フェーズに入る。バニラ（764）が送る Registry Data（0x05）は
   765形式（0x05）へ変換して中継する。Add Resource Pack は764の
   Resource Pack Send（0x06、UUIDなし）を765の Add（0x07、UUID付き）に
   変換する。Tags はレジストリ番号がずれるため落とす。
4. Finish Configuration（0x02）を中継し、クライアントの応答（0x02）が
   バニラに届いた時点で両方ともプレイ状態に入る。
5. バニラが送るJoin Game（764の0x29）は765の0x29へ変換する。764と765で
   形式は同じためペイロードはそのまま通す。
6. スポーンは765式。Spawn Position（0x54）が合図。

下向き変換（765→764）は、上向き（764→765）の対応表を起動時に反転して
使い回す（手書きの新規表なし）。763クライアントは763→764の直接変換
（合成表）で参加する。くわしくは `docs/PROXY-REVERSE.md` を参照。

### 766クライアントの流れ（内部763／764／765／766）

`minecraft-version` で内部プロトコルが決まり、766クライアントの流れは
内部で分かれる。くわしくは `docs/PROXY-1.20.5.md` を参照。

1. ハンドシェイクのプロトコルVarIntを766→内部プロトコルに書き換えてバニラへ送る。
2. Login Startは765・764と同形式（名前＋UUID）のため変換しない。
   Login Successは766だけ末尾に `strictErrorHandling` の bool が付くため、
   プロキシが付け直す。
3. 内部766のときは素通し（リレー）。内部764／765のときは設定フェーズを中継し、
   Registry Data の形式（codec NBT→エントリ配列）だけ変換する。
   内部763のときは設定フェーズが無いため、プロキシが Join Game の codec から
   Registry Data（766形式 0x07）と Finish Configuration を合成して送る。
4. バニラが送るJoin Game は766の 0x2B へ変換する（dimension は番号から文字列に戻す）。
5. スポーンは766式。Spawn Position（0x56）が合図。
6. 内部766のバニラは Java 21 で起動する（`VanillaServerHost.javaBinaryFor`：
   `detergentmc.java21.home`→`DETERGENTMC_JAVA21_HOME`→現在の Java）。

766のスロットはデータコンポーネント形式のため、Window Click／Set Creative Slot は
古いサーバー向けに変換できず落とす（ネイティブの766⇔766ではリレーのため問題ない）。

### 暗号化・圧縮の扱い

- **圧縮は無効化する。** バニラの `server.properties` には
  `network-compression-threshold=-1` を書き、バニラ側の圧縮を止める。
  クライアント側にも Set Compression を送らない。バニラが万一
  Set Compression を送ってきた場合、プロキシはクライアントを切断する
  （zlibの展開・再圧縮はこの段階では扱わない）。
- **765は暗号化があっても素通し。** リレーはバイト列をそのまま通すので、
  online-modeの暗号化ハンドシェイクもプロキシを素通りし、クライアントと
  バニラが直接認証する。プロキシは秘密鍵も共有秘密も見ない。
- **763＋online-modeはプロキシ認証で参加できる。** 763を翻訳するにはプロキシが
  パケットの中身を読まなければならず、そのためにはクライアント⇔プロキシ間
  の暗号化をプロキシが解かなければならない。内部バニラに認証を任せたままの
  MITMは成立しないが、認証の主体をプロキシに移せば成立する（Velocity／
  BungeeCordと同じ考え方）。プロキシがEncryption Requestを送り、クライアントの
  Encryption Responseから共有秘密とverify tokenを取り、serverIdハッシュで
  Mojangセッションサーバーへ照会し、認証済みUUID・名前・プロパティを確定させて
  から、内部バニラにはoffline-modeの信頼済み接続として繋ぐ。内部バニラは
  `127.0.0.1` のみで `online-mode` を常に `false` で書き出す。認証失敗時は
  理由付きLogin Disconnectで切断する。くわしくは `docs/PROXY-1.20.1.md` の
  「1.20.1クライアント（763、online-mode）」を参照。
