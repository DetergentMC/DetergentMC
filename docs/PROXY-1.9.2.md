# 1.9.2クライアント／サーバー（プロトコル109）の対応

DetergentMC に **109（Minecraft 1.9.2）** を追加した記録。
隣接バージョンは 110（1.9.4／1.9.3）で、このツリーでは 110 の
1段下として配線した。110 との差分は **1.9.3 で起きた変更**で、
①クライアント行き update_sign が 109 にはあり（0x46）、後続
6パケットの ID が +1 ずれる、②Chunk Data に blockEntities
フィールドが無い、の2点。**レジストリ差分はゼロ**（実測で
三重に確認）で、変換表は 110 の表を全面委譲する。

> **状態（2026-11-19時点）：Stage E 完了。**
> 分割検証の件数は末尾の「検証」節を参照。ProxyIntegrationTest への
> 統合セル追加と実バニラ統合テストは実施済み。**本物の
> ゲームクライアントでの確認は未実施**（全バージョン共通）。

## 番号対応（重要）

- **プロトコル 109 ＝ Minecraft 1.9.2 単独**（先行調査で実 jar を
  実測し、Status 応答のプロトコルが 109 であることを確認。
  1.9.3／1.9.4 は 110）。world_version は **176**。
- 降下順は 110 → 109 → 108（1.9.1）。108 とは差分ゼロの見込み
  （先行調査済み）だが、それは 108 実装時に実測で確定する。

## 確定した事実（すべて実測）

- **バニラ 1.9.2 サーバーjar**：piston-meta から取得。
  SHA-1 `2b95cc7b136017e064c46d04a5825fe4cfa1be30`
  （piston-meta の version json の downloads.server.sha1 と
  一致、照合済み）、8,848,002 バイト。**jar ルートに version.json
  が無く、pack.mcmeta も data/ も無い世代**（110／210 と同じ型）。
  プロトコルは **109**（実バニラを起動し Status 応答で確認）、
  pack_format は **2**（**この世代にデータパックは存在しない**）、
  world_version は **176**（起動したワールドの level.dat の
  DataVersion で確認）、内部サーバーは **Java 8 世代**
  （version json の javaVersion は jre-legacy）。data-generator
  は無い。
- **protocol.json 全面比較（Stage A、tools/packet-ids-109.py）**：
  109 ⇔ 110 は toClient 総数 119 ⇔ 118。109 にだけあるのは
  クライアント行き **update_sign** のみで、ID 差分はその後ろの
  **ちょうど6件**（sound_effect 0x47、playerlist_header 0x48、
  collect 0x49、entity_teleport 0x4a、entity_update_attributes
  0x4b、entity_effect 0x4c。いずれも 109 = 110 + 1）。types
  セクションは完全一致で、フィールド構造の差分は
  **map_chunk と update_sign の2件だけ**（map_chunk の差分は
  blockEntities の有無）。PacketIds は 284 エントリになり、
  109 で存在するのは 114 件（110 は 113 件）。
- **レジストリ差分ゼロの三重確認**：①ローカル minecraft-data の
  dataPaths.json が 1.9.2／1.9.4 の全レジストリキーで同じ
  pc/1.9 を指す、②両実 jar の en_US.lang の差分は 1.9.3 で
  追加された /stopsound のコマンド説明 5 行のみ（レジストリ名の
  差分なし）、③ブロック 214 種・アイテム 365 種が pc/1.9 の
  件数と一致。よって 109 の変換表は 110 の表を全面委譲できる。
- **Keep Alive は varint**（109⇔110 で KA 変換は不要）。
  先行調査のワイヤ採取で KA 本体（4バイトの varint）を読み切り、
  応答（サーバー行き 0x0b）が受け付けられ、その後のチャットが
  バニラのログに到達することを確認した。340 以上との境界では
  既存の KA 付け替え（110 と共用の変換＋109 専用の復元表）が
  働く。
- **Join Game の dimension は i32**（110 と同一。107 の i8 とは
  違う）。先行調査の採取で 20/20 バイト消費を確認。
- チャンクは 110 と同じ骨格で、末尾はバイオーム u8×256。
  **blockEntities フィールドは無い**（付いたのは 110 から）。

## 110 との差分（確定内容）

### パケット

- クライアント行き **update_sign（0x46）が 109 にだけある**。
  110 で削除され、後続6件の ID が −1 ずれた（109 では +1）。
  サーバー行き update_sign は両方にある（0x19、差分なし）。
- update_sign は正準（758）側に同名パケットが無いため、
  109 サーバー→新クライアント方向では**落とす**（警告のみ）。
  335 の prepare_crafting_grid と同じ扱い。109 クライアント
  方向へは、看板の内容は Block Entity Data／チャンク経由では
  運ばれないため、看板テキストのライブ更新はこの世代では
  届かない（下記「残る制限」）。

### 形式差分（ちょうど 1 件）

- **map_chunk の blockEntities**：110 ではチャンク末尾に
  count (varint)＋NBT 配列があるが、109 には無い。
  110 方向→109 では読み捨て、109→110 方向では空（count 0）を
  補う。したがって **109 バックエンドのチャンクではブロック
  エンティティの中身（看板の文字・チェストの中身等）は
  運ばれない**。110⇔210 の扱い（210 にはある／109 には無い）
  と整合させた。なお 109⇔110 の境界以外（109⇔758 等の合成
  経路）でも同じで、758 側のブロックエンティティは 109 向け
  チャンクでは落ち、109 側からは空が補われる。

これ以外の形式は 110 と同一：音の pitch は両者とも u8
（換算は 110 と同じ ×63.5 量子化）、resource_pack_receive の
先頭 hash は両者ともあり、spawn_entity_living の種別は u8、
title の action 番号・collect・block_place のカーソル i8・
スロット形式・メタデータ型（i8、型 0–12）も同一。

### レジストリ

**差分ゼロ**（上記の三重確認）。109 の RegistryRemapper 写像は
全メソッドが 110 の写像へ委譲し、`RegistryRemapper109Test` が
全入力域で 110 と一致することを固定している。近似も 110 と
同じ（次節）。

## 近似方針

レジストリが 110 と同一のため、近似は 110 のものをそのまま
引き継ぐ（新→109 方向）：

- magma（213）→ netherrack（87）、nether_wart_block（214）／
  red_nether_brick（215）→ nether_brick（112）、
  bone_block（216）→ quartz_block（155、メタ保持）、
  structure_void（217）→ barrier（166）、アイテム形も同じ対応
  （structure_block のアイテム形 255 → barrier のアイテム形
  166。アイテム形自体が 1.9 系に存在しないため）。
- polar_bear → ブタ（90）、fallingdust → explode（0）、
  1.10 追加音 19 件 → 汎用音（block.stone.break の 109 側
  インデックス 364。110 と同値）。
- 109 固有の損失：チャンクのブロックエンティティが運ばれない
  （上記）、クライアント行き update_sign が正準経路で落ちる
  （上記）。

## 実装の形

- 変換経路は 110 の経路を写したもの（ChunkTranslator／
  SlotTranslator の 109 節、PlayTranslator の JoinGame109、
  ProxySession の 109 系メソッド群）。110 節との違いは
  チャンク末尾の blockEntities 読み書きの有無だけで、
  それ以外は 110 の境界処理（音 pitch 換算、resource_pack の
  hash 付け外し、KA 復元表）を 109 用に写した。
  レジストリ写像は RegistryRemapper の 109 節が全て 110 へ
  委譲する。
- リソースパックは **pack_format 2**。レイアウトは 1.13 より
  前の旧形式（textures/items/）で、110 と形式番号も同じ。
  フォールバック順は **109 → 110 → 210 → 315 → 316 → 335 →
  …**。外部設定キーは `resource-pack.url-109`／
  `resource-pack.sha1-109`。
- アダプタモジュールは `detergentmc-adapter-v1_9_2`。
  内部サーバーは 1.9.2 の指定でプロトコル 109 として扱い、
  Java 8 で起動する。
- Bedrock→109 の生物スポーンは専用の parseSpawnEntity109／
  parseSpawnEntityLiving109 から **110 のパースへ委譲**する
  （種別表が 110 と完全同一のため。種別番号が違う 498 の
  関数には流さない）。

## 検証

- 分割検証 `split-verification-109/`（重複排除後の集計）：
  **4,348 件・失敗 0・エラー 0**（内訳：protocol 3,515 件、
  bedrock 449 件、core 314 件（うち統合セル 62 件）、adapters
  67 件、content 3 件。スキップ 39 件は環境条件付き自己
  スキップで、110 の分割検証と同じ内訳）。
- **Stage E 完了**：ProxyIntegrationTest に 109 の新規 3 セル
  （fake109→実バニラ 1.9.2、fake109→実バニラ 1.9.4、
  fake110→実バニラ 1.9.2）＋回帰 59 セル（110 の Stage E の
  選定をすべて含む）の **62 セルすべてが合格**（スキップ 0、
  各セルの XML をメソッド名と照合済み）。新規 3 セルとも
  参加→チャット→Keep Alive（0x1f、varint、応答 0x0b）→
  応答後の2通目のチャットがバニラログに到達、まで実ワイヤで
  確認した。Stage E は 110 最終 HEAD `b294c50` へのリベース
  （競合なし）の上で実施した。
- **resource_pack_receive の空 hash は実バニラ 1.9.2 が
  受け付けることを確認した**：fake110→実バニラ 1.9.2 セルで、
  110 形式（ダミー hash＋result）の Resource Pack Response を
  送信 → プロキシはクライアント側境界で hash を読み捨て、
  109 向けに空文字列の hash を先頭へ補って転送 → バニラは
  切断せず、その後の Keep Alive 往復と2通目のチャット到達・
  接続維持を確認した。
  最古プロトコル脱落の罠は `ClientAdapter109Test` で固定した
  （一覧の先頭が 109、110・210・315・316 が残り、計 38
  プロトコル）。
- Stage A では実バニラ 1.9.2 を起動して Status を確認し、
  protocol.json 全面比較と jar 内データの突き合わせで差分を
  確定した（tools/packet-ids-109.py が検証スクリプト）。

## 残る制限

- **本物のゲームクライアントでの確認は未実施**（全バージョン
  共通）。実バニラ統合テスト（Stage E）は完了しているが、
  形式差分2件の見え方（チャンクのブロックエンティティ欠落、
  看板のライブ更新）、近似の見え方、Keep Alive の長時間
  セッションでの安定性、2 人同時参加時の相互表示は実機確認の
  重点である。
- **チャンクのブロックエンティティが 109 では運ばれない**
  （看板の文字・チェストの中身・バナーの模様等は 109 が
  関わるチャンクでは欠落する。1.9.2 のワイヤ形式自体に
  載せ場が無いための世代的な制限）。
- **クライアント行き update_sign が正準経路で落ちる**ため、
  109 サーバーで看板を書き換えても新クライアントには
  ライブ更新が届かない。
- resource_pack_receive の空 hash は実バニラ 1.9.2 が受け付ける
  ことを Stage E で確認済み（「検証」節を参照）。
- データパックが無い世代のため trigger ブリッジ（言語切替・
  hello 等）は 109 バックエンドでは使えない（110／210／315／
  316 から引き継ぐ既知の課題、代替は未定）。
- 近似の損失：1.10 追加ブロック 5 種の見た目（110 と同じ
  代用）、polar_bear の姿（ブタ代用）、fallingdust の表現、
  1.10 追加音 19 件（汎用音）、音 pitch の量子化誤差。
- Declare Recipes／Statistics／Tags／World Event ID は全方向で
  未実装（落とす）のまま（全バージョン共通）。
