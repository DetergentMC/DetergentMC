## 0. この手順書の読み方

DetergentMC の 109 対応は **Stage E まで完了**。単体テスト
（分割検証 4,348 件・失敗 0）と実バニラ統合テスト（新規 3 セル
＋回帰 59 セルの 62 セルすべて合格）で確認済みだが、
**本物のゲームクライアントでの確認は未実施**。この
チェックリストはその実機確認のためのものである。

109 は 1.9.2 単独プロトコルで、110（1.9.4／1.9.3）との差分は
1.9.3 の変更2点（クライアント行き update_sign の有無と後続
6件の ID のずれ、Chunk Data の blockEntities の有無）だけで、
レジストリは 110 と完全同一。実機では特に、**チャンクの
ブロックエンティティ欠落の見え方**（看板の文字・チェストの
中身が 109 経由では出ない）、**看板のライブ更新が届かない
こと**、110 から引き継ぐ**近似の見え方**と **Keep Alive
（varint）の長時間セッションでの安定性**が重点になる。

### A. 単体テストで検証済みの項目（実機では再現の確認）

- 109 のパケット ID 表が 110 と「update_sign の有無＋後続
  6件の +1 ずれ」だけで違うこと（`PacketIds109Test`：
  全 284 エントリで規則を固定。109 に存在するのは 114 件）。
- 対応クライアント一覧の最古が 109 で、110／210／315／316 が
  残り、計 38 プロトコル（`ClientAdapter109Test`。最古脱落の
  罠を固定）。
- レジストリ写像が全入力域で 110 と一致すること
  （`RegistryRemapper109Test`。委譲の正しさを固定）。
- チャンクの blockEntities 欠落の境界処理
  （`ChunkTranslator109Test`：109 形式に末尾が無いこと、
  758 側のブロックエンティティが 109 向けで落ちること、
  109→758 で空の列が補われること）。
- クライアント行き update_sign が正準経路で落ちること、
  sound_effect が 109 では 0x47 で届き pitch が u8 化される
  こと（`ProxySession109Test`）。

### B. 実機でしか確認できない項目

- [ ] 1.9.2 クライアントで 1.9.2 サーバー（内部）に参加し、
      チャンク表示・移動・チャットが正常か。
- [ ] 1.9.2 クライアントで新しいサーバー（例：1.20.4）に
      参加できるか。音のピッチが極端にずれて聞こえないか。
- [ ] 新しいクライアント（例：1.20.4）で 1.9.2 サーバーに
      参加し、看板の文字・チェストの中身がどう見えるか
      （109 のチャンクにはブロックエンティティが載らない
      ため、欠落が前提。エラーや切断にならないことの確認）。
- [ ] 1.9.2 サーバー側で看板を書き換えたとき、新しい
      クライアントにライブ更新が届かないこと（仕様どおりの
      制限であることの確認。切断やエラーにはならないこと）。
- [ ] リソースパックの要求→応答の流れが 1.9.2 クライアントで
      完走するか（空 hash の受け付け自体は Stage E の統合
      テストで確認済み。実機での流れの確認）。
- [ ] polar_bear のいる場所でブタとして表示されるか
      （1.9.2 クライアント→新しいサーバー）。
- [ ] Keep Alive（varint）世代のため、30 分以上の接続で
      切断されないか。
- [ ] 2 人以上のプレイヤーが互いに見えるか（全バージョン
      共通の最優先確認項目。偽クライアントでは検証不能）。
