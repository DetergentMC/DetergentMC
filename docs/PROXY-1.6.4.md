# プロトコル78（Minecraft 1.6.4）— Netty 以前世代フロントエンド

DetergentMC が Netty 以前世代（1.6.4 以前）のクライアントとバックエンドを
受けるための別フロントエンド（モジュール `detergentmc-legacy-frontend`）の
記録。既存の Netty 世代の経路（プロトコル4〜777）には一切影響しない。

**状態：Stage A〜E 完了（2026-11-20）。**
**本物の 1.6.4 クライアントでの確認は未実施。**
分割検証（リベース＋Stage E 修正後の最終ツリー）：**4,725 件・
合格 4,688 件・失敗 0・スキップ 37 件**（統合セル 81 件＝Netty 側
回帰 77 セル＋レガシー新規 4 セルを含む。集計は
`split-verification-78/`、最終監査で全セルの XML 存在と
テストケース名の一致を確認済み）。

## 番号の規律（重要）

旧世代のプロトコル番号は新世代と衝突する（例：旧47＝1.4.2、新47＝1.8）。
そのため：

- 旧世代の番号は `detergentmc-legacy-frontend` モジュール内にだけ置く
  （`io.detergentmc.legacy.LegacyProtocol` / `LegacyPacketTable`）。
- `io.detergentmc.protocol.ProtocolVersion` / `PacketIds` には絶対に足さない。
- 旧世代に言及するときは「レガシー プロトコル78（1.6.4）」のように書く。
- 対応一覧は分けて数える：Netty 世代 43 プロトコル（25565番）＋
  レガシー 1 プロトコル（レガシー用ポート）。

## Stage A で実測確定した事項（2026-11-19）

土台：実バニラ 1.6.4 サーバー jar（piston-meta から取得、SHA-1
`050f93c1f3fe9e2052398f7bd6aca10c63d64a87` を再検証）を JDK 8 で起動し、
jar のバイトコード解析＋実ワイヤ採取（スポーン有効）の両方で確定した。

- **パケット表**：jar の登録コードから 82 個の ID と方向フラグを機械抽出。
  各パケットの read メソッドから読み取りスキーマを抽出して
  `LegacyPacketTable` に固定した。検証：prep の採取（45パケット）、
  60秒採取（1,331パケット）、歩行採取（2,199パケット）の3本すべてを
  表どおりに末尾まで完全解析（ズレ0）。
- **entityMetadata**：ヘッダバイト `(型<<5)|(index&31)`、終端 **0x7F**、
  型は **7種のみ**（0=byte, 1=short, 2=int, 3=float, 4=string(最大64文字),
  5=slot, 6=位置(i32×3)）。1.7 の型7（回転）は 78 には無い。型0〜6の
  番号は 1.7 と一致。実ワイヤでも確認（プレイヤー自身・Spawn Mob・
  Entity Metadata パケット）。
- **スロット内 NBT**：i16 長＋**gzip 圧縮 NBT**（プロトコル5と同じ形）。
  スロット骨格は i16 アイテムID（-1=空）、u8 個数、i16 ダメージ。
- **0x04 time**：i64 が **2個**（ワールド時刻＋昼時刻）。
- **テクスチャパック配送**：専用パケットは無く、ログイン直後に
  プラグインメッセージ **0xFA チャンネル `MC|TPack`** で届く。
  データは `URLのバイト列 + 0x00 + サイズの10進文字列`
  （実バニラはサイズとして 16 を送ることを採取で確認）。
- **チャンク**：バルク 0x38 のヘッダはプロトコル5と完全同一
  （i16 個数、i32 圧縮長、u8 スカイライト有無、圧縮データ、末尾に
  チャンクごとの x/z/ビットマップ）。セクション中身（10240バイト式）
  は 1.7 と同一レイアウト。単体チャンク 0x33 は実ワイヤには現れなかった
  （1.6.4 サーバーは更新もバルクで送る）。0x33 のヘッダはバイトコードで確定。
- **ログイン列**：0x02 → 0xFD（暗号化要求）→ 0xFC → 0xFC →
  AES/CFB8 開始 → 0x01。offline-mode でも暗号化は省略されない（再確認）。
  ログイン本体は `i32 プロトコル, string レベル種別, u8×5`
  （gamemode＋hardcoreビット / 次元 / 難易度 / 高さ / 最大人数）。
- **スポーン種別 ID**：実ワイヤで 55=スライム（サイズはメタデータ16番）、
  92=ウシを確認。プロトコル5（1.7）と同じ番号空間の継続とみなす。
- **運用知見**：旧バックエンドは、参加処理が落ち着く前に play パケットを
  送ると "Protocol error, unexpected packet" で切断する。フロントエンドは
  参加完了までクライアントの play パケットを保持しなければならず、
  バックエンド側クライアントとしても参加列の完了を待つ必要がある。
  また Java の loopback 接続には `-Djava.net.preferIPv4Stack=true` が必須。

## 設計（Stage B〜D）

- **別ポート**で待ち受ける（既定 25568、設定 `legacy.port`）。
  25565 を先頭バイトで判別する案は、検証済みの Netty 経路に危険が
  及ぶため採らない。無効時（既定は無効、`legacy.enabled`）は従来どおり。
- **ブリッジモード（既定）**：レガシークライアントのログインを終端し、
  コアのプロキシ（127.0.0.1:`server.port`）へ **プロトコル5の
  クライアントとして** 接続して play パケットを中継・変換する。
  プロトコル5の play レイアウトが内部ハイブリッド形式そのもので、
  検証済みの変換器を全部再利用できるため。コア側は offline モードが前提
  （合成クライアントは Mojang 認証を通せない。旧世代は元々 offline 前提）。
- **ダイレクトモード**：内部サーバーが 1.6.4（`minecraft-version: "1.6.4"`）
  のときはコアがバックエンドと話せないため、フロントエンドが内部バニラへ
  レガシークライアントとして直接接続する（暗号化含む）。この構成では
  現代クライアントは参加できない（今回の範囲外として明記）。
- **暗号化**：クライアント面では RSA 1024bit 鍵ペアで終端し AES/CFB8、
  バックエンド面では旧クライアントとして開始する。CFB8 は
  `Cipher.update()` を直接使う（ストリーム経由だとバイトを抱え込む）。
- **旧世代は offline 前提**：旧クライアントの online 認証は Mojang の
  旧エンドポイント廃止のため成立しない。設計として割り切る。

## 変換の近似・破棄（Stage B の判断）

- **1.7 で追加されたブロック**は 1.6.4 の近似に化ける（ステンドグラス→
  ガラス、ステンドグラス板→ガラス板、アカシア／ダークオークの葉→葉、
  原木→原木、階段→オーク階段、氷塊→氷、ダブルプラント→赤い花）。
  チャンク内・ブロック変更・スロットのすべてで同じ表を使う。
- **メタデータ型7（回転）** は 78 に無いため落とす。
- **落下ブロックのメタ値** は落とす（ブロック ID のみ送る。data が
  0 になると速度フィールドの条件が崩れるため、その場合は砂で代用）。
- **マップ（0x34）と統計（0x37）** は双方向とも落とす（78 側の
  対応形式への変換を持たない）。
- **パーティクル** は名前文字列のまま変換する（78 と内部形式で
  同じ形のため）。
- **タブ補完** は候補を NUL 連結した1文字列にする（1.6.4 サーバーの
  実装と同じ形式を採取で確認）。
- チャットは JSON コンポーネントを平文に潰す（色コード § は保持）。

### Stage E で見つけて直した実バグ（4件）

1. **VanillaLogParser が 1.7 以前のログ接頭辞を読めなかった**：
   旧形式の行頭（`2026-11-19 14:08:48 [INFO] `）を剥がせず、
   ホストした 1.6.4 バックエンドの起動完了・参加・チャット
   イベントが一切発生しなかった。旧接頭辞のパターンを追加し
   テスト 4 件で固定。
2. **暗号化ハンドシェイクの順序が両面とも誤っていた**：
   サーバーの 0xFC は**平文**で届く（暗号化は両者の 0xFC
   交換の後）。`LegacyBackendLogin` は自分の 0xFC を送った
   直後に暗号化を有効化してサーバーの 0xFC を復号読みして
   おり、`LegacySession` は自分の 0xFC を暗号化して送って
   いた。A〜D の偽ピア E2E は両側が同じ誤りを共有して
   自己整合していたため検出できず、実バニラで初めて判明。
3. **ログイン列に 0xCD Client Status が欠けていた**：実バニラ
   1.6.4 は 0xCD（payload 0＝初期スポーン）が来るまで
   ログインを完了せず、接続がデッドロックした。
   `LegacyBackendLogin` が 0x01 の後に送り、
   `LegacySession` が消費するよう修正（prep の採取
   CaptureOld3 が正解だった）。
4. **パケット表の移動系 onGround が U8 になっていた**：
   0x0D（および 0x0A／0x0B／0x0C）の onGround フィールドは
   実ワイヤでは boolean。ブリッジ変換器が Boolean を生成する
   ため
   `ClassCastException` で参加直後にセッションが死んだ。
   表を BOOL に直し、変換器の読み替えも統一した。
   ダイレクトモードはバイト同一の素通しのため無症状だった。

## 制限（正直な一覧）

- 本物の 1.6.4 クライアントでの確認は未実施（検証はレガシー
  偽クライアント＋実バニラの統合テストと単体テスト）。
- 旧世代は offline 前提（online 認証は成立しない）。ブリッジモードは
  コアプロキシも offline モードで動いている必要がある。
- ダイレクトモード（1.6.4 バックエンド）では現代クライアントは参加できない。
- 単体チャンク 0x33 のスカイライト有無は圧縮データの長さから推定する
  （ヘッダにフラグが無いため）。推定できない形は素通しする。
- スポーンオブジェクトの回転バイト（ピッチ／ヨー）の対応はワイヤ順の
  素直な対応を仮置きした（間違っていてもヨーとピッチが入れ替わるだけ）。
- 変換の近似・破棄は PLAYTEST-1.6.4.md とコード内コメントにも記載。
