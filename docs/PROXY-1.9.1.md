# 1.9.1クライアント／サーバー（プロトコル108）の対応

DetergentMC に **108（Minecraft 1.9.1）** を追加した記録。
隣接バージョンは 109（1.9.2）で、このツリーでは 109 の
1段下として配線した。109 との差分は **ゼロ**（Stage A で
実測により証明。下記）。変換表・パケット ID 列・ワイヤ形式は
すべて 109 と同一で、108 の変換は 109 の表を全面委譲する。
315⇔316、480⇔485、477⇔480 と同じ「差分ゼロ」の型である。

> **状態（2026-11-19時点）：Stage E 完了。**
> 分割検証の件数は末尾の「検証」節を参照。ProxyIntegrationTest への
> 統合セル追加と実バニラ統合テストは実施済み。**本物の
> ゲームクライアントでの確認は未実施**（全バージョン共通）。

## 番号対応（重要）

- **プロトコル 108 ＝ Minecraft 1.9.1 単独**（実バニラ 1.9.1 を
  起動し、Status 応答のプロトコルが 108 であることを確認。
  1.9.2 は 109、1.9.3／1.9.4 は 110）。world_version は **175**。
- 降下順は 109 → 108 → 107（1.9）。107 とは Join Game の
  dimension の型（107 は i8、108 以降は i32）が違うことが
  先行調査で分かっている。

## 確定した事実（すべて実測）

- **バニラ 1.9.1 サーバーjar**：piston-meta から取得。
  SHA-1 `bf95d9118d9b4b827f524c878efd275125b56181`
  （piston-meta の version json の downloads.server.sha1 と
  一致、照合済み）、8,848,010 バイト。**jar ルートに version.json
  が無く、pack.mcmeta も data/ も無い世代**（109／110 と同じ型）。
  プロトコルは **108**（実バニラを起動し Status 応答で確認）、
  pack_format は **2**（**この世代にデータパックは存在しない**）、
  world_version は **175**（起動したワールドの level.dat の
  DataVersion で確認）、内部サーバーは **Java 8 世代**
  （version json の javaVersion は jre-legacy）。data-generator
  は無い。
- **108⇔109 差分ゼロの証明（Stage A）**：
  1. **実 jar 同士の全面比較**：1.9.1／1.9.2 両 jar のエントリ
     一覧が完全一致（各 6,354 件、片方にしか無いエントリは
     ゼロ）。非クラスファイルは **CRC まで全て一致**。差分が
     あるのはクラス 11 件（ass、azg、b$1、em、la、mc、
     net/minecraft/server/MinecraftServer、pb、pc、qw、zj）
     のみで、その文字列定数の差分はバージョン文字列
     （"1.9.1"／"1.9.2"、Outdated 系メッセージ）と em.class の
     エラーメッセージ文言 1 件（"IntArray with size " ⇔
     "VarIntArray with size "）だけで、**レジストリ登録名の
     文字列には差分が無い**。
  2. **実バニラ 1.9.1 のワイヤ採取**：Status は
     `{"name":"1.9.1","protocol":108}` を自己申告。Join Game は
     20 バイトで dimension を i32 として読んで過不足なし
     （i8 で読むと壊れる）。Chunk Data はバッファ末尾までの
     残量 0（blockEntities フィールド無し＝109 と同じ形）。
     Keep Alive 本体 `98c4c401` を varint として 4/4 バイト
     消費し、応答（サーバー行き 0x0b）の後のチャットが
     バニラのログに到達した。
  3. **先行調査の採取との一致**：Keep Alive 本体
     （`d9efb803`＝7223257 の varint）、Join Game の採取
     （1.9.1／1.9.2 とも 20 バイト、エンティティ ID より後ろは
     完全一致）。
  4. **DataVersion**：1.9.1 は 175、1.9.2 は 176（level.dat
     の NBT から実測。この2つが両版の実質的な唯一の
     データ差分だが、ワイヤ形式・レジストリには影響しない）。
- minecraft-data には **pc/1.9.1 のデータ自体が存在しない**
  （dataPaths に "1.9.1" の項目が無く、あるのは 1.9、
  1.9.1-pre2、1.9.2、1.9.4）。ground truth は pc/1.9.2
  （109 のもの）＋上記の実測である。
- **Keep Alive は varint**（109⇔108 で KA 変換は不要。
  340 以上との境界では 109 と共用の付け替え＋108 専用の
  復元表が働く）。

## 109 との差分（確定内容）

**ゼロ。** パケット集合・ID 列（PacketIds は 284 エントリ、
108 で存在するのは 114 件＝109 と同数）、フィールド構造、
レジストリ（ブロック 214 種・アイテム 365 種・音 444 件・
エンティティ・バイオーム・パーティクル・効果）はすべて
109 と同一。検証スクリプトは tools/packet-ids-108.py
（108 の列＝109 の列のコピーであることを全エントリで確認）。

そのため 110 との関係も 109 と同じになる：クライアント行き
update_sign が 108 にもあり（0x46、正準経路では落とす）、
後続 6 件の ID が 110 より +1 ずれ、Chunk Data に
blockEntities フィールドが無い（108 バックエンドのチャンク
ではブロックエンティティの中身は運ばれない）。近似も 109
（＝110）と同じものを引き継ぐ：magma→netherrack（87）、
nether_wart_block／red_nether_brick→nether_brick（112）、
bone_block→quartz_block（155、メタ保持）、structure_void→
barrier（166）、structure_block のアイテム形→barrier の
アイテム形（166）、polar_bear→ブタ（90）、fallingdust→
explode（0）、1.10 追加音 19 件→汎用音、音 pitch の ×63.5
量子化。

## 実装の形

- 変換経路は 109 の経路を写したもの（ChunkTranslator／
  SlotTranslator の 108 節、PlayTranslator の JoinGame108、
  ProxySession の 108 系メソッド群）。中身は 109 の境界処理
  （チャンク末尾の blockEntities 無し、音 pitch 換算、
  resource_pack の hash 付け外し、KA 復元表）を 108 用に
  写したもので、RegistryRemapper の 108 節は全メソッドが
  109 の写像へ委譲する。
- リソースパックは **pack_format 2**。レイアウトは 1.13 より
  前の旧形式（textures/items/）で、109 と形式番号も同じ。
  フォールバック順は **108 → 109 → 110 → 210 → 315 → 316 →
  335 → …**。外部設定キーは `resource-pack.url-108`／
  `resource-pack.sha1-108`。
- アダプタモジュールは `detergentmc-adapter-v1_9_1`。
  内部サーバーは 1.9.1 の指定でプロトコル 108 として扱い、
  Java 8 で起動する。
- Bedrock→108 の生物スポーンは専用の parseSpawnEntity108／
  parseSpawnEntityLiving108 から **109 のパースへ委譲**する
  （種別表が 109 と完全同一のため。種別番号が違う 498 の
  関数には流さない）。

## 検証

- 分割検証 `split-verification-108/`（重複排除後の集計）：
  **4,431 件・失敗 0・エラー 0**（内訳：protocol 3,592 件、
  bedrock 451 件、core 318 件（うち統合セル 65 件）、adapters
  67 件、content 3 件。スキップ 39 件は環境条件付き自己
  スキップで、109 の分割検証と同じ内訳）。最古プロトコル
  脱落の罠は `ClientAdapter108Test` で固定した（一覧の先頭が
  108、109・110・210・315・316・335・338・340 が残り、計 39
  プロトコル）。
- **Stage E 完了**：ProxyIntegrationTest に 108 の新規 3 セル
  （fake108→実バニラ 1.9.1、fake108→実バニラ 1.9.2、
  fake109→実バニラ 1.9.1）＋回帰 62 セル（109 の Stage E の
  選定をすべて含む）の **65 セルすべてが合格**（スキップ 0、
  各セルの XML をメソッド名と照合済み）。新規 3 セルとも
  参加→チャット→Keep Alive（0x1f、varint、応答 0x0b）→
  応答後の2通目のチャットがバニラログに到達、まで実ワイヤで
  確認した。Stage E は 109 最終 HEAD `30c8895` へのリベース
  （競合なし）の上で実施した。
- **resource_pack_receive の空 hash は実バニラ 1.9.1 が
  受け付けることを確認した**：fake109→実バニラ 1.9.1 セルで、
  109 形式（ダミー hash＋result）の Resource Pack Response を
  送信 → プロキシはクライアント側境界で hash を読み捨て、
  108 向けに空文字列の hash を先頭へ補って転送 → バニラは
  切断せず、その後の Keep Alive 往復と2通目のチャット到達・
  接続維持を確認した。
- 回帰セル fake335→実バニラ 1.13 が「Keep Alive 応答後の
  チャット到達の制限時間超過」で繰り返し失敗した（108 ツリー
  で3回、対照として 109 ツリーでも1回、同型）。109 の
  Stage E では初回で合格していたセルであり、合格回の
  バニラログにもサーバーの処理遅延（Can't keep up）が
  記録されていることから、負荷時のタイミング由来と判断した
  （210／110 の Stage E でも同セルに同じ事象）。最終的には
  合格し、上記の 65 セル全合格に含まれる。
- Stage A では実バニラ 1.9.1 を起動して Status を確認し、
  実 jar 同士の全面比較とワイヤ採取で差分ゼロを証明した
  （tools/packet-ids-108.py が検証スクリプト）。

## 残る制限

- **本物のゲームクライアントでの確認は未実施**（全バージョン
  共通）。実バニラ統合テスト（Stage E）は完了しているが、
  チャンクのブロックエンティティ欠落の見え方、看板のライブ
  更新が届かないこと、近似の見え方、Keep Alive の長時間
  セッションでの安定性、2 人同時参加時の相互表示は実機確認の
  重点である。
- **チャンクのブロックエンティティが 108 では運ばれない**
  （109 から引き継ぐ世代的な制限。看板の文字・チェストの
  中身・バナーの模様等は 108 が関わるチャンクでは欠落する）。
- **クライアント行き update_sign が正準経路で落ちる**ため、
  108 サーバーで看板を書き換えても新クライアントには
  ライブ更新が届かない（109 から引き継ぐ制限）。
- resource_pack_receive の空 hash は実バニラ 1.9.1 が受け付ける
  ことを Stage E で確認済み（「検証」節を参照）。
- データパックが無い世代のため trigger ブリッジ（言語切替・
  hello 等）は 108 バックエンドでは使えない（109／110／210／
  315／316 から引き継ぐ既知の課題、代替は未定）。
- 近似の損失：1.10 追加ブロック 5 種の見た目（109 と同じ
  代用）、polar_bear の姿（ブタ代用）、fallingdust の表現、
  1.10 追加音 19 件（汎用音）、音 pitch の量子化誤差。
- Declare Recipes／Statistics／Tags／World Event ID は全方向で
  未実装（落とす）のまま（全バージョン共通）。
